# Эксплуатация базы знаний

Приложение работает постоянно. Данные — SQLite, изображения и CSRF-ключ — находятся в `KB_DATA_DIR`. Команды обслуживания не выводят пароли/токены. Образ не содержит shell, Node.js или sqlite CLI: используйте встроенные команды `/app/kb`.

## Первоначальный администратор

Создаётся **до запуска HTTP-сервера**, только на пустой базе. Передайте временный пароль через stdin; не вписывайте его в командную строку, `.env` или историю shell. При первом входе администратор обязан сменить его. После этого пользователи создаются через «Управление → Сотрудники».

## Срок входа

Сессия действует 7 суток с момента входа, без продления при запросах. Срок одинаков для записи в SQLite и cookie `kb_session` в браузере. Перезапуск сервера сохраняет сессии. Выход завершает текущую сессию; смена или сброс пароля и блокировка пользователя отзывают все его сессии. Ранее выданные сессии сохраняют прежний срок: для недельного входа нужно войти заново после обновления приложения.

## Резервные копии

На работающем сервисе:

```sh
docker compose exec -T knowledgebase-app /app/kb backup
```

Каталог берётся из `KB_BACKUP_DIR` (`/backups` в Compose). Комплект содержит согласованный снимок БД, изображения, CSRF-ключ и `manifest.json` с SHA-256. Подтверждённые изменения из WAL включаются. Копирование живого `.db` командой `cp` некорректно.

Команда автоматически оставляет 14 последних завершённых комплектов. Ошибка новой копии не удаляет предыдущую. Незавершённые `.incomplete-*` не считаются копиями. Не удаляйте содержимое завершённых комплектов вручную: несовпадение checksum блокирует восстановление.

Пример ежедневного cron на хосте (путь поправьте под установку):

```cron
0 2 * * * cd /opt/knowledgebase && docker compose exec -T knowledgebase-app /app/kb backup >>/var/log/knowledgebase-backup.log 2>&1
30 2 * * * cd /opt/knowledgebase && docker compose exec -T knowledgebase-app /app/kb maintenance >>/var/log/knowledgebase-maintenance.log 2>&1
```

Время задаётся часовым поясом cron хоста. Настройте доставку ошибок и перенос завершённых комплектов на независимый носитель/сервер: том на том же диске не защищает от его поломки. Периодически проверяйте restore.

## Восстановление

Остановите только базу знаний. Сохраните старый каталог данных переименованием/архивом; подготовьте новый пустой `data` с владельцем UID/GID 65532. Не удаляйте старые данные, пока не проверили восстановление.

```sh
docker compose stop knowledgebase-app
# Сохраните существующий ./data вне нового каталога восстановления.
# Подготовьте новый пустой ./data и установите владельца 65532:65532.
docker compose run --rm --no-deps knowledgebase-app restore --from /backups/ИМЯ_КОМПЛЕКТА --target /data
docker compose up -d knowledgebase-app
docker compose exec -T knowledgebase-app /app/kb check
```

Проверяются checksum и SQLite integrity/foreign keys. Непустой целевой каталог не перезаписывается. Restore отказывается работать при активном сервере, открытой CLI-операции с БД или неизвестном формате комплекта. Старые сессии отзываются; пользователи входят заново со своими паролями. Флаг обязательной смены временного пароля также сохраняется.

Если восстановление было прервано при установке файлов, маркер `restore-in-progress` блокирует старт приложения. Сохраните этот каталог и повторите восстановление в новый пустой; не удаляйте маркер для обхода проверки.

Для контрольного восстановления используйте другую папку, другой Compose-проект и отдельную сеть. Не подключайте контрольную копию к рабочему домену и не используйте рабочий том.

## Обслуживание и ограничения

`maintenance` удаляет непривязанные изображения старше 24 часов и просроченные записи сессий/ограничений входа. Удаление файлов координируется с backup блокировкой. Опубликованные изображения и изображения личных черновиков не удаляются. Команды могут временно ждать завершения друг друга.

SQLite должна находиться на локальном диске. Запускайте ровно один HTTP-экземпляр над томом. При ошибке миграции сервис не объявляет готовность; исправьте причину/восстановите согласованную копию. Не заменяйте SQLite-файлы под работающим процессом.

При обновлении сначала сделайте backup. Миграции применяются автоматически до готовности HTTP; откат образа после изменения схемы требует совместимости или восстановления копии. Клиентские Compose-проекты не останавливаются.

## Развёртывание в отдельной папке

Основной production-путь — [автодеплой из GitHub Actions](deployment.md): образ собирается в CI, передаётся архивом по SSH, загружается через `docker load` и запускается в `/opt/knowledgebase` без исходников на сервере. Registry не нужен. Серверный `.env` не изменяется, тег образа сохраняется в `compose.override.yaml`. Выполняйте обычные команды обслуживания из `/opt/knowledgebase`, чтобы Compose учитывал оба файла.

Для ручной установки можно собрать образ в checkout: `docker build -t knowledgebase:local .` и доставить его через registry или `docker save`/`docker load`. На сервере достаточно Docker Engine с Compose, компиляторы не нужны.

Для новой ручной установки в отдельную `/opt/knowledgebase` скопируйте `deploy/compose.yaml` и `deploy/.env.example` как `.env`; существующий `.env` не перезаписывайте. Укажите настоящий HTTPS-домен; если не используете `compose.override.yaml`, добавьте `KB_IMAGE=имя:тег` доставленного образа в `.env`. Создайте `data` и `backups` с правами 0700 и владельцем 65532:65532 (обычно через sudo на хосте). Не используйте общие тома клиентских приложений.

```sh
cd /opt/knowledgebase
docker network create knowledgebase-ingress
docker compose config --quiet
```

Если сеть уже существует, сначала проверьте её назначение, а не пересоздавайте её. Имена сетей в обоих проектах должны совпадать. Не запускайте `docker system prune` или `compose down` клиентского проекта.

Bootstrap без сохранения пароля в истории (Bash, терминал оператора):

```bash
read -r -s -p 'Временный пароль администратора: ' kb_bootstrap_password
printf '\n'
printf '%s\n' "$kb_bootstrap_password" | docker compose run --rm --no-deps -T knowledgebase-app admin create --login admin --name 'Администратор' --password-stdin
unset kb_bootstrap_password
docker compose up -d
docker compose exec -T knowledgebase-app /app/kb check
```

После первого входа смените пароль, создайте категории и учётные записи сотрудников. Публичной регистрации и демонстрационных пользователей нет.

## Nginx из другого Compose-проекта

База не публикует порты хоста. Только текущий Nginx владеет 80/443. Сервис специально называется `knowledgebase-app`, а не `app`, чтобы при подключении новой сети к Nginx не добавить конфликтующий DNS-алиас для существующего клиентского сервиса `app`.

1. В **исходном** Compose Nginx сохраните все прежние сети и добавьте внешнюю `knowledgebase-ingress`. Пример — `deploy/nginx-compose.fragment.yaml`; замените имя сервиса и список прежних сетей фактическими, не копируйте фрагмент поверх всего файла.
2. Подключите работающий контейнер Nginx к сети командой `docker network connect knowledgebase-ingress ФАКТИЧЕСКИЙ_ID_NGINX`. Это не требует перезапуска. Сохранённое изменение Compose нужно для последующих пересозданий. Альтернатива — в его папке `docker compose up -d --no-deps ИМЯ_СЕРВИСА_NGINX` с коротким согласованным перерывом входящего трафика. Обычный reload сети не добавляет.
3. Проверьте `nginx -v`: конфигурация требует Nginx **1.27.3 или новее** (тестируется на 1.28). Подключите `deploy/nginx-upstream.conf.example` в контексте `http {}`, вне `server {}`. Он задаёт динамическое DNS-разрешение и пул keepalive: без пула постоянный поток запросов исчерпывает исходящие порты. Затем создайте **новый** виртуальный хост `server_name kb.ваша-компания...` с сертификатом вашим обычным способом. Внутри него разместите содержимое `deploy/nginx-site.conf.example` либо подключите его как include. Не меняйте `location /` существующего клиентского домена. Файл примера — location-фрагмент, самостоятельно он не является полным конфигом Nginx.
4. Проверьте конфигурацию через `docker exec ФАКТИЧЕСКИЙ_ID_NGINX nginx -t`, затем `docker exec ФАКТИЧЕСКИЙ_ID_NGINX nginx -s reload`.

Nginx обращается к `knowledgebase-app:8080`, не к `localhost`. DNS разрешается заново через Docker resolver; после смены IP при обновлении приложения маршрут восстанавливается в пределах TTL 10 секунд плюс старт сервиса. На этом промежутке допустимы короткие 502. Внешняя сеть не удаляется при остановке одного из проектов.

## Ресурсы и диагностика

Контейнер ограничен 768 МиБ без добавочного swap, Go GC настроен на 512 МиБ. БД находится в том же процессе. Дополнительный расход общего Nginx проверяется отдельно; память чужих клиентских приложений в бюджет базы не входит.

```sh
docker compose ps
docker compose logs --tail=100 knowledgebase-app
docker compose exec -T knowledgebase-app /app/kb metrics
```

`metrics` читает cgroup v2: current, peak, limit и OOM-kill count. Это включает файловый кеш, а не только heap Go; отсутствие метрик возвращает ошибку. Сама команда кратковременно добавляет процесс в тот же cgroup. `/readyz` проверяет SQLite, `/healthz` — HTTP; ни один не заменяет функциональную проверку входа/статьи.

Для локальной разработки без HTTPS: `KB_DEV=true`, `KB_PUBLIC_URL=http://127.0.0.1:8080`, `KB_DATA_DIR=./data`. HTTP dev-режим разрешён только для loopback-адресов; production Compose его не включает.

## Локально через Docker Compose

Из корня репозитория используйте `compose-local.yaml`. Node.js и Go на ПК не нужны. Конфигурация предназначена для локального запуска и открывает порт только на `127.0.0.1`.

Если раньше приложение запускалось командой `docker run --name knowledgebase-local ...`, сначала остановите **этот** контейнер:

```sh
docker stop knowledgebase-local
```

Compose использует тот же том `knowledgebase-local-data`, поэтому пользователи и статьи сохраняются. Не запускайте старый контейнер и Compose одновременно над этим томом. Если данные ранее хранились в другом томе или в папке, сначала укажите существующее хранилище в конфигурации, не удаляйте его.

Если администратор уже есть:

```sh
git switch feat/knowledge-base
git pull --ff-only
docker compose -f compose-local.yaml up -d --build
```

Откройте **http://127.0.0.1:8081/login**. После обновления страницы тема будет соответствовать системной; последующие изменения системной темы применяются сразу.

При самом первом запуске, на пустом томе, сначала соберите образ и создайте администратора **до запуска сервера**. В Bash / Git Bash / WSL:

```bash
docker compose -f compose-local.yaml build
read -r -s -p 'Временный пароль администратора: ' kb_bootstrap_password
printf '\n'
printf '%s\n' "$kb_bootstrap_password" | docker compose -f compose-local.yaml run --rm --no-deps -T knowledgebase-app admin create --login admin --name 'Администратор' --password-stdin
unset kb_bootstrap_password
docker compose -f compose-local.yaml up -d
```

Если Compose уже запущен над пустой базой, остановите сервис перед созданием администратора: `docker compose -f compose-local.yaml stop knowledgebase-app`. Команда создания откажется менять непустую базу: повторно создавать администратора при обновлениях не нужно.

Диагностика и остановка:

```sh
docker compose -f compose-local.yaml ps
docker compose -f compose-local.yaml logs --tail=50 knowledgebase-app
docker compose -f compose-local.yaml exec knowledgebase-app /app/kb check
docker compose -f compose-local.yaml down
```

Обычный `down` сохраняет тома. Не добавляйте `--volumes` / `-v`, если хотите сохранить данные.

### Если при входе возникает 403

Адрес в браузере должен точно совпадать с `KB_PUBLIC_URL`: схема, имя хоста и порт. В локальном Compose это `http://127.0.0.1:8081`; `localhost` считается другим источником. Настройки фиксированы в YAML и не зависят от производственного `.env`.

После перехода со старого контейнера откройте `/login` заново и повторите вход. При сообщении «Недопустимый запрос. Обновите страницу.» очистите данные сайта для `127.0.0.1` или проверьте вход в приватном окне: форма и CSRF-cookie должны относиться к одному запуску приложения. Не отключайте CSRF-проверку.

Неверный пароль или временное ограничение попыток входа возвращают 401, а не 403. Если ошибка остаётся, нужны точный текст ответа и сведения о контейнере, обслуживающем порт 8081. Пароли и содержимое базы для диагностики не присылайте.

### Если вчерашний пароль перестал работать

Пароли находятся в SQLite-базе в каталоге `/data`, а не в Docker-образе. Пересборка образа и пересоздание контейнера с **тем же** хранилищем не сбрасывают их. Локальный Compose всегда подключает том с явным именем `knowledgebase-local-data`; учётная запись из другого тома или bind-папки в нём не появится автоматически.

1. После пяти неверных попыток вход ограничивается на 10 минут. Дождитесь окончания окна и повторите вход с правильным логином. Сообщение в форме одинаково для неверных данных и ограничения попыток.
2. Посмотрите контейнеры и тома без удаления:

   ```sh
   docker ps -a --format "{{.Names}} | {{.Image}} | {{.Status}}"
   docker volume ls --format "{{.Name}}"
   ```

3. Для старого и нового контейнера посмотрите только подключения хранилищ (замените `ИМЯ_КОНТЕЙНЕРА` на найденное имя):

   ```sh
   docker inspect ИМЯ_КОНТЕЙНЕРА --format '{{range .Mounts}}{{println .Type .Name .Source "->" .Destination}}{{end}}'
   ```

   Сравните источник, подключённый к `/data`. Другое имя тома или другой путь означает другую базу. Сначала определите старое хранилище и сохраните его; не переносите SQLite-файлы из работающего сервера простым копированием.
4. Если сервер уже использовал тот же том, проверьте раскладку, точный логин и блокировку. Для сброса пароля используйте другого администратора через «Управление → Сотрудники»; создание нового первого администратора не изменяет непустую базу.

Не выполняйте `docker compose down -v`, `docker volume rm` или `docker system prune --volumes` для исправления входа. Если прежний запуск был без постоянного тома, данные могут оставаться в файловой системе старого контейнера — сохраните его до диагностики.

## Доступ агентов через MCP

MCP встроен в основной контейнер и доступен по `/mcp` на том же HTTPS-домене.
Ключи сотрудники создают на странице «Доступ агента». Порты и контейнеры
добавлять не требуется. [Подключение клиентов и управление ключами](mcp.md).
