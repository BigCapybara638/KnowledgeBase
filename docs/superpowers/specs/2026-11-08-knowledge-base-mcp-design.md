# MCP для базы знаний

Дата: 2026-11-08. Статус: реализовано с авторизацией ключами;
[результаты проверки](../../validation/mcp-2026-11-08.md).

Проверка отдельным разработчиком завершена: важных неразрешённых вопросов
для составления плана реализации не выявлено.

## Назначение

Локальный агент сотрудника находит опубликованные статьи корпоративной базы
знаний, читает их содержание и получает постоянные ссылки для ссылок в ответе.
Статьи остаются в существующем приложении; на компьютеры сотрудников база
данных не копируется.

Пользователь попросил MCP для разных агентов, без привязки к одному продукту,
и выбрал встраивание MCP в текущее приложение.

Это дополнение затрагивает сервер, управление ключами, интерфейс подключения,
локальный адаптер и документацию. Параметры, которые пользователь не выбирал
отдельно, ниже обозначены как предложения разработчика.

## Исходное состояние и ограничения

- Один постоянно работающий контейнер Go, SQLite на локальном томе,
  существующий Nginx с HTTPS. Общий бюджет решения — до 1 ГБ ОЗУ.
- `internal/articles` уже читает опубликованные неархивные статьи и списки
  с проверкой действующего пользователя.
- `internal/search` использует SQLite FTS5: поиск по названию и полному тексту,
  до 20 результатов на страницу, запрос до 256 символов.
- Все действующие пользователи после смены временного пароля могут читать
  все опубликованные статьи. Личные черновики доступны только их владельцам.
- Вход в браузере использует cookie на 12 часов и защиту CSRF. Долгоживущих
  ключей доступа и программного интерфейса сейчас нет.
- Опубликованная статья содержит документ Tiptap, готовый `plain_text`,
  категорию, авторов, версию и даты. Размер документа ограничен 2 МиБ.
- Текущий сервер и хранилище используют Linux. На компьютере разработки Go
  отсутствует, доступен Docker; серверные проверки выполняются в контейнере.

## Рассмотренные подходы

| Подход | Возможности и цена | Решение |
| --- | --- | --- |
| MCP внутри текущего Go-приложения | Общие статьи, поиск, пользователи и контейнер; MCP обновляется вместе с приложением | Выбран пользователем |
| Отдельный MCP-сервис | Независимое обновление; потребуются дополнительное развёртывание и интерфейс к базе | Не выбран |

## Предлагаемый результат

1. У базы появляется адрес `https://<домен-базы>/mcp`.
2. Сотрудник входит на сайт, открывает «Доступ агента», создаёт именованный ключ
   и один раз копирует его в настройки агента.
3. Клиент со Streamable HTTP подключается по адресу и передаёт
   `Authorization: Bearer <ключ>`.
4. Для клиента со stdio запускается небольшой `kb-mcp` на компьютере
   сотрудника. Он связывает стандартный MCP через stdin/stdout с тем же
   защищённым сервером. База и дополнительные серверы на ПК не нужны.
5. Агент ищет статьи, читает нужную статью и приводит её исходную ссылку.
6. Сотрудник может отозвать свой ключ. Заблокированный пользователь теряет
   доступ всеми ключами.

Название страницы и управление собственными ключами — предложения
разработчика, исходящие из существующей модели учётных записей.

## Совместимость

Использовать официальный `github.com/modelcontextprotocol/go-sdk` в стабильной
версии, зафиксированной в `go.mod` и `go.sum`. Доступная проверенная версия
на момент проектирования — v1.8.0; при реализации проверить её доступность
в используемом Go module proxy.

Поддержать два стандартных способа подключения:

- Streamable HTTP для клиентов с настройкой URL и Bearer-заголовка;
- stdio через поставляемый адаптер для клиентов, запускающих локальную команду.

Версии протокола согласовывает SDK; использовать доступную обратную
совместимость SDK и проверить как новый, так и предыдущий поддерживаемый
протокол. Не писать собственный JSON-RPC или обработчик handshake.

Термин «разные агенты» означает совместимость с этими стандартными
интерфейсами. Нельзя обещать работу с любой версией любого продукта без
проверки его настроек. Клиент, принимающий исключительно OAuth и не допускающий
Bearer-заголовок или локальную команду, требует отдельной OAuth-интеграции;
она в данный предлагаемый объём не включена. Старый HTTP+SSE отдельно
не реализуется. Эти границы — предложения разработчика для первой версии.

## Сервер и границы доступа

Добавить `internal/mcpserver`, использующий существующие сервисы статей,
категорий и поиска. Подключить его в `web.App` к `/mcp` до браузерной CSRF-обёртки.
Все браузерные маршруты управления ключами остаются под текущей сессией и CSRF.

MCP использует только Bearer-ключ. Cookie браузера и обычный session-токен
не дают доступ к `/mcp`; MCP-ключ не даёт вход в браузерные маршруты.
На каждом HTTP-запросе проверяются ключ, срок действия и текущий пользователь;
личность передаётся обработчикам через контекст запроса или механизм TokenInfo
SDK, без глобального изменяемого пользователя.

Предложение разработчика: stateless Streamable HTTP с JSON-ответами.
Для чтения статей не нужны фоновые подписки, запросы к клиенту и хранение
долгоживущих сессий. Отзыв ключа действует на последующий запрос, включая
запросы уже подключившегося агента. Выполняющийся запрос может завершиться.

Для MCP сохранить `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`
и ограничение тела запроса до 1 МиБ; обработку ограничить 15 секундами.
Проверять `Origin`, если он передан: разрешён только настроенный `KB_PUBLIC_URL`.
Запросы без Origin от локальных MCP-клиентов разрешены при действующем ключе.
Широкий CORS не включать. Ссылки строить только из `KB_PUBLIC_URL` и ID статьи,
не из клиентского Host или proxy-заголовков.

Без ключа или при недействующем ключе возвращать HTTP 401 с Bearer challenge,
без редиректа на HTML-страницу входа. Ошибки аргументов, отсутствие статьи
и ошибки чтения оформлять стандартными средствами SDK. Внутренние SQL-ошибки,
секреты и пути файлов клиенту не выдавать.

## Инструменты агента

Все четыре инструмента объявляются только для чтения, без побочных эффектов.
Результат доступен как структурированный JSON и как текст, чтобы им могли
пользоваться клиенты без отображения structured content.

| Инструмент | Аргументы | Результат |
| --- | --- | --- |
| `search_articles` | `query`, `page` (по умолчанию 1) | До 20 совпадений: ID, заголовок, фрагмент, категория, автор, URL; признак следующей страницы |
| `list_articles` | Необязательные `category_id`, `page` (по умолчанию 1) | До 20 карточек опубликованных статей и признак следующей страницы |
| `get_article` | `id`, `offset` (по умолчанию 0), `limit` (по умолчанию 12000) | Текст статьи, ID, заголовок, категория, авторы, версия, даты, URL, общий размер и следующая позиция |
| `list_categories` | `page` (по умолчанию 1) | До 100 категорий: ID, название, порядок; признак следующей страницы |

Пагинация категорий может быть добавлена в существующий сервис без изменения
браузерного поведения. Все входные параметры ограничиваются и проверяются
сервером, в том числе отрицательные и чрезмерные номера страниц.

Предложение разработчика: `get_article` возвращает сохранённый `plain_text`.
Позиция и длина считаются в Unicode-символах, чтобы не разрезать русский текст.
Максимум одной части — 20000 символов; за концом статьи — пустая часть
с отсутствующей следующей позицией. Текст не обрезается без указания следующей
позиции. Пустая строка поиска использует существующее поведение списка статей.

Разметка и исходные вложения доступны по ссылке в браузере с обычной
авторизацией. Изображения и видео через MCP не передаются. Форматирование
и адреса ссылок, которых нет в `plain_text`, не восстанавливаются; это явно
указывается в документации. Создание, редактирование, удаление, черновики,
архив и административные операции через MCP не предоставляются.

## Ключи доступа

Добавить миграцию с таблицей ключей: ID, пользователь, название, SHA-256
секретной части/полного ключа, время создания, истечение, время отзыва.
Индексировать уникальный хеш и список ключей пользователя.

Предложения разработчика:

- Секрет: `kb_mcp_` и минимум 32 криптографически случайных байта в base64url.
- Ключ привязан к одному пользователю и разрешает только чтение MCP.
- Название: от 1 до 80 символов. До 20 действующих ключей на пользователя.
- Срок действия выбирается из 30, 90 или 365 дней; по умолчанию 90 дней.
- Сырой ключ показывается один раз после создания на странице с `no-store`.
  В списке остаются название, даты и статус. В URL, логи и Git ключ не попадает.
- Создавать, просматривать и отзывать можно только собственные ключи;
  операции изменения защищены существующей CSRF-защитой и проверкой пользователя.
- Доступ запрещён для отсутствующего/заблокированного пользователя и до
  обязательной смены пароля, даже если ключ ещё действителен.
- Смена и административный сброс пароля отзывают все ключи пользователя
  в той же транзакции. Выход из браузера ключи агента не отзывает.
- История ограничена 100 записями, действующие ключи показываются первыми.
  Блокировка дополнительно отзывает ключи навсегда, как браузерные сессии.
- Последнее использование не записывается на каждый запрос: чтение статей
  не создаёт постоянную нагрузку на SQLite writer.

Обратная миграция удаляет только новую таблицу; текущие статьи, черновики
и сессии не меняются.

## Локальный адаптер stdio

Отдельная команда `cmd/kb-mcp` зависит от SDK и сетевого клиента, но не
импортирует Linux-хранилище приложения. Её можно собирать для Windows,
macOS и Linux без установленной SQLite и без копирования БД.

Конфигурация через окружение: `KB_MCP_URL` и `KB_MCP_TOKEN`.
URL обязан использовать HTTPS; HTTP допускается только для loopback при
локальной разработке. Запретить credentials, fragment и секреты в query URL.
Не следовать HTTP-редиректам с ключом. Проверку TLS-сертификатов не отключать.

Адаптер соединяется с удалённым MCP, получает определения инструментов и
публикует их локальному клиенту; вызовы передаются удалённому серверу с
ограничением времени и сохранением результатов/ошибок. Использовать SDK
для обеих сторон; не писать самостоятельный построчный JSON-RPC proxy.
Отмена операции и закрытие stdin завершают соединение и процесс.
stdout содержит исключительно MCP; диагностика идёт в stderr без ключей.

Статический набор из четырёх инструментов не требует подписок на изменение
их списка. При изменении состава инструментов клиент переподключается.

## Развёртывание и документация

Основной MCP работает внутри существующего `kb serve`, на текущем порту,
томе и домене. Не добавлять отдельную БД, контейнер, Redis или векторный поиск.
Для JSON-ответов обычного проксирования существующего Nginx достаточно;
проверить, что Authorization доходит до приложения и не появляется в логах.

Добавить `docs/mcp.md`: создание/отзыв ключа, HTTP-подключение с заголовком,
stdio-конфигурация с env, сборка адаптера для трёх ОС, ограничения содержимого
статей и диагностика ошибок 401. В примерах использовать только placeholders.
Связать инструкцию с README и эксплуатационной документацией.

Конкретные примеры настроек сторонних агентов включать только после проверки
их актуальной официальной документации. Универсальные примеры имеют приоритет;
устанавливать плагины в агенты пользователя или менять их настройки не требуется.

## Проверка результата

- Проверки ключей: однократная выдача секрета, хранение только хеша,
  принадлежность пользователю, истечение, отзыв, блокировка, смена/сброс пароля,
  лимит действующих ключей. CSRF и изоляция чужих ключей на браузерных маршрутах.
- Клиент официального SDK подключается к HTTP `/mcp`, перечисляет четыре
  инструмента, находит опубликованную статью, читает её и получает правильный URL.
- Неопубликованные, архивные статьи и личные черновики не раскрываются
  ни через поиск, ни через список, ни по известному ID.
- Кириллица, разбиение длинного текста и ограничение результатов работают
  без потери символов и без бесконтрольного роста ответа.
- Ключ нельзя заменить браузерной cookie; отозванный ключ перестаёт работать
  на следующем запросе. Запрос с недопустимым Origin отклоняется.
- Тот же сценарий проходит через реальный stdio-процесс адаптера; stdout
  остаётся корректным MCP, секрет не появляется в stderr.
- Адаптер собирается для Windows, macOS, Linux; фактический запуск проверяется
  на доступной ОС. Результаты сборки не выдаются за запуск на каждой ОС.
- Существующие Go-тесты, сборка UI и Docker-сборка проходят; браузерный сценарий
  страницы ключей проверяется отдельно от рабочей базы пользователя.

## Что решает разработчик при реализации

Имена Go-типов и файлов, SQL индексы, детали SDK, обработку стандартных MCP
ошибок, конкретный способ упаковки двоичных файлов и тестовые fixtures.
В рамках этих решений нельзя расширять доступ агента до изменения статей,
раздавать общий ключ всем сотрудникам или обходить проверку пользователя.
